## 0. 시험장에서 설계하는 순서

시험은 "주어진 실습파일을 가지고 하나의 앱을 작성"하는 방식이라, 빈 프로젝트가 아니라 **이미 일부가 만들어진 파일에 기능을 채우는** 상황일 가능성이 높다. 그래서 코드를 쓰기 전에 아래 순서로 3분만 설계한다.

1. **요구사항에서 세 가지를 뽑는다**: 화면(어떤 화면이 몇 개?) / 데이터(무엇을 저장하고 보여주나?) / 이벤트(사용자가 무엇을 누르면 무슨 일이?)
2. **xml의 id부터 확인한다**: ViewBinding은 xml id를 카멜 표기로 바꾼 이름(`btn_add` → `btnAdd`)을 쓰므로, 코드에서 쓸 이름이 여기서 정해진다.
3. **데이터 클래스(Entity)** → **Dao/Database** → **Adapter** → **Activity/Fragment 연결** → **이벤트** 순서로 채운다. 아래에서 위로 쌓으면 빨간 줄(미해결 참조)이 덜 생긴다.
4. 기능 하나 만들 때마다 **실행해서 확인**한다. 마지막에 몰아서 실행하면 어디서 틀렸는지 찾기 어렵다.

### 요구사항을 보고 구성요소 고르기

| 이런 요구가 나오면 | 이렇게 설계한다 |
|---|---|
| 탭이나 메뉴로 화면 몇 개를 전환 | Fragment 여러 개 + navigation graph + BottomNavigationView 또는 NavigationView. **메뉴 item id = graph의 fragment id** |
| 목록에서 하나를 누르면 상세 화면 | 화면 이동이면 nav `<action>` + `bundleOf`, 같은 화면에서 띄우면 커스텀 다이얼로그 |
| 같은 모양의 항목이 여러 개 반복 | RecyclerView + 항목 xml + ViewHolder + Adapter + LayoutManager |
| 앱을 껐다 켜도 데이터가 남아야 함 | Room(Entity, Dao, Database) 또는 SQLiteOpenHelper |
| 선택값이 바뀔 때마다 화면 갱신 | 해당 위젯에 리스너 등록 (체크박스, 라디오그룹, 스피너, 레이팅바) |
| 여러 위젯이 같은 처리를 함 | 리스너 객체를 **하나 만들어 공유** (수업의 스피너 필터 방식) |
| 등록 화면과 수정 화면이 거의 같음 | 다이얼로그 함수 하나 + `existingItem: Item?`가 null이면 등록, 아니면 수정 |
| 작성자만 수정/삭제 가능 | `item.ownerId != currentUser`이면 Toast 후 `return` |

## 문제 1. 운동 기록 화면: 이벤트 리스너 연결하기

**중요도 ★★★ / 범위: 이벤트 처리 (3주차 운동 기록 실습과 같은 화면 구성)**

### 상황

운동 기록 앱의 입력 화면이 xml로 이미 만들어져 있다. 사용자가 무언가를 바꿀 때마다 화면 아래 요약 문구가 **버튼을 누르지 않아도 바로** 바뀌어야 한다.

### 요구사항

1. 체크박스 `cbWarmUp`(준비운동), `cbCoolDown`(정리운동)을 체크/해제할 때마다 `tvCheck`에 "완료 항목: 준비운동, 정리운동" 형태로 표시. 아무것도 없으면 "완료 항목이 없습니다."
2. 라디오그룹 `rgType`(`rbRun` 달리기, `rbWalk` 걷기, `rbBike` 자전거)에서 선택이 바뀌면 `tvType`에 "운동 종류: 달리기"
3. 레이팅바 `ratingIntensity`(별 5개, 1점 단위)를 바꾸면 `tvIntensity`에 "운동 강도: 3점"
4. 메모 `etMemo`에 입력할 때마다 `tvMemoCount`에 "12 / 50" 처럼 글자 수 표시
5. `btnSave` 클릭: 메모가 비어 있으면 Toast "메모를 입력하세요"만 띄우고 끝. 아니면 Toast "저장되었습니다"
6. `btnSave` **롱클릭**: 모든 입력을 초기화하고 Toast "초기화"

### 설계 판단

- 요구 1~4는 "값이 바뀔 때마다"이므로 **버튼 클릭 한 번으로 처리하면 안 되고**, 각 위젯에 맞는 리스너를 등록해야 한다.
- 체크박스 두 개는 같은 일(요약 갱신)을 하므로 **요약 함수 `updateCheckSummary()`를 하나 만들고** 두 리스너가 모두 이 함수를 호출하게 한다. 3주차 실습 코드의 `updateCheckSummary()`가 바로 이 구조다. [수업]
- 라디오버튼은 개별 버튼이 아니라 **RadioGroup에** 리스너를 단다. 어느 버튼이 선택됐는지는 `checkedId`로 구분한다.
- 롱클릭 리스너는 **Boolean을 반환**해야 한다. true를 반환해야 "처리 완료"로 보고 일반 클릭이 이어서 발생하지 않는다.

| 위젯 | 리스너 등록 메소드 | 람다 매개변수 |
|---|---|---|
| CheckBox, Switch | `setOnCheckedChangeListener` | `(buttonView, isChecked)` |
| RadioGroup | `setOnCheckedChangeListener` | `(group, checkedId)` |
| RatingBar | `setOnRatingBarChangeListener` | `(ratingBar, rating, fromUser)` |
| EditText | `addTextChangedListener(TextWatcher)` | 메소드 3개 재정의 |
| Button | `setOnClickListener` / `setOnLongClickListener` | `(v)` / `(v)` 후 Boolean 반환 |

### 구현 순서

1. `onCreate`에서 binding 준비 (`ActivityMainBinding.inflate(layoutInflater)`, `setContentView(binding.root)`)
2. 요약 함수 `updateCheckSummary()` 작성
3. 체크박스 2개에 리스너 등록 → 각각 요약 함수 호출
4. RadioGroup, RatingBar, EditText 리스너 등록
5. 버튼 클릭, 롱클릭 등록
6. 실행: 체크, 라디오, 별점, 입력을 하나씩 바꾸며 요약이 즉시 바뀌는지 확인

xml에서 확인할 속성 (레이팅바):

```xml
<RatingBar
    android:id="@+id/ratingIntensity"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:numStars="5"
    android:stepSize="1"
    android:rating="0" />
```

```kotlin
class MainActivity : AppCompatActivity() {
    lateinit var binding: ActivityMainBinding

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        binding = ActivityMainBinding.inflate(layoutInflater)
        setContentView(binding.root)

        // 1) 체크박스 두 개가 같은 함수를 호출
        binding.cbWarmUp.setOnCheckedChangeListener { buttonView, isChecked ->
            updateCheckSummary()
        }
        binding.cbCoolDown.setOnCheckedChangeListener { buttonView, isChecked ->
            updateCheckSummary()
        }

        // 2) 라디오그룹: 어떤 버튼이 선택됐는지 checkedId로 구분
        binding.rgType.setOnCheckedChangeListener { group, checkedId ->
            val type = when (checkedId) {
                R.id.rbRun -> "달리기"
                R.id.rbWalk -> "걷기"
                else -> "자전거"
            }
            binding.tvType.text = "운동 종류: $type"
        }

        // 3) 레이팅바: rating은 Float
        binding.ratingIntensity.setOnRatingBarChangeListener { ratingBar, rating, fromUser ->
            binding.tvIntensity.text = "운동 강도: ${rating.toInt()}점"
        }

        // 4) 글자 수: TextWatcher는 메소드 3개를 모두 재정의해야 함
        binding.etMemo.addTextChangedListener(object : TextWatcher {
            override fun beforeTextChanged(s: CharSequence?, start: Int, count: Int, after: Int) {}
            override fun onTextChanged(s: CharSequence?, start: Int, before: Int, count: Int) {
                binding.tvMemoCount.text = "${s?.length ?: 0} / 50"
            }
            override fun afterTextChanged(s: Editable?) {}
        })

        // 5) 클릭: 검증 실패 시 람다에서 빠져나오기
        binding.btnSave.setOnClickListener {
            if (binding.etMemo.text.toString().trim().isEmpty()) {
                Toast.makeText(this, "메모를 입력하세요", Toast.LENGTH_SHORT).show()
                return@setOnClickListener
            }
            Toast.makeText(this, "저장되었습니다", Toast.LENGTH_SHORT).show()
        }

        // 6) 롱클릭: true 반환
        binding.btnSave.setOnLongClickListener {
            binding.cbWarmUp.isChecked = false
            binding.cbCoolDown.isChecked = false
            binding.rgType.clearCheck()
            binding.ratingIntensity.rating = 0f
            binding.etMemo.setText("")
            Toast.makeText(this, "초기화", Toast.LENGTH_SHORT).show()
            return@setOnLongClickListener true
        }
    }

    // 3주차 실습 코드와 같은 구조
    private fun updateCheckSummary() {
        val completedItems = StringBuffer()
        if (binding.cbWarmUp.isChecked) completedItems.append("준비운동")
        if (binding.cbCoolDown.isChecked) {
            if (completedItems.isNotEmpty()) completedItems.append(", ")
            completedItems.append("정리운동")
        }
        binding.tvCheck.text = if (completedItems.isEmpty()) "완료 항목이 없습니다."
                               else "완료 항목: $completedItems"
    }
}
```

### 동작 흐름

사용자가 체크박스를 누름 → 시스템이 체크 상태를 바꿈 → 등록해 둔 리스너의 람다가 자동 호출(콜백) → `updateCheckSummary()`가 두 체크박스의 **현재 상태를 다시 읽어서** 문구를 새로 만든다. 그래서 어느 체크박스를 눌러도 결과가 항상 정확하다. 롱클릭에서 `isChecked = false`로 바꾸면 체크 리스너도 다시 호출되어 요약이 자동으로 "완료 항목이 없습니다."가 된다.

### 시험 빈칸 후보

- `setOnRatingBarChangeListener { ratingBar, rating, fromUser -> ... }` 의 매개변수 3개
- `RadioGroup` 리스너의 `checkedId`와 `R.id.rbRun` 비교
- `return@setOnLongClickListener true`
- xml `android:numStars`, `android:stepSize`, `android:rating`
- `Toast.makeText(this, "...", Toast.LENGTH_SHORT).show()`

### 자주 하는 실수

- `Toast.makeText(...)`만 쓰고 **`.show()` 누락**
- 라디오버튼마다 클릭 리스너를 따로 단다 (동작은 하지만 선택 해제 시점을 놓침). RadioGroup에 한 번 등록하는 것이 정석
- 롱클릭 람다에서 마지막 줄을 Boolean이 아닌 문장으로 끝냄 → 컴파일 오류
- `rating`은 Float라 그대로 출력하면 "3.0점"이 됨 → `toInt()`

## 문제 2. 스피너 두 개로 목록 필터링

**중요도 ★★★ / 범위: 이벤트 처리 + 어댑터뷰 (AA_SQLite 필터와 같은 구조)**

### 상황

분실물 목록 화면 위에 스피너가 두 개 있다. 하나는 종류(전체, 분실물, 습득물), 하나는 상태(전체, 진행중, 완료). 두 스피너 중 **어느 것을 바꾸든** 두 조건을 모두 반영한 목록이 보여야 한다.

### 요구사항

1. 종류 스피너 `spinnerTypeFilter`는 **코드에서** 배열로 항목을 채운다.
2. 상태 스피너 `spinnerStatusFilter`는 **xml의 `android:entries`** 로 항목을 채운다.
3. 두 스피너 중 하나라도 선택이 바뀌면 어댑터의 `setFilters(type위치, status위치)`를 호출한다.
4. 처음 화면이 뜰 때는 "전체, 전체"로 모든 항목이 보인다.

### 설계 판단

- 스피너도 어댑터뷰다. 데이터를 직접 갖지 않고 **ArrayAdapter**가 항목을 공급한다.
- 두 스피너 모두 "두 값을 읽어서 필터 적용"이라는 **같은 일**을 하므로, `OnItemSelectedListener` 객체를 **하나 만들고 두 스피너에 같이 등록**한다. [수업] 리스너 안에서는 `position` 대신 **두 스피너의 `selectedItemPosition`을 모두 읽는다** (어느 스피너가 바뀌었는지 신경 쓰지 않아도 됨).
- `OnItemSelectedListener`는 인터페이스라 메소드 2개(`onItemSelected`, `onNothingSelected`)를 **모두** 재정의해야 해서 람다가 아닌 `object :` 익명 객체로 만든다.
- 필터 로직은 어댑터에 둔다. 어댑터가 `allitems`(전체)와 `items`(화면에 보일 것) 두 리스트를 갖고, `filter { }`로 조건에 맞는 것만 `items`에 넣는다. [수업]

### 구현 순서

1. `res/values/arrays.xml`에 상태 배열 작성, 상태 스피너 xml에 `android:entries` 지정
2. 코드에서 종류 배열 + `ArrayAdapter` 생성 → 종류 스피너에 연결
3. 리스너 객체 1개 작성 → 두 스피너의 `onItemSelectedListener`에 대입
4. 어댑터에 `setFilters()`, `applyFilters()` 작성
5. 실행: 종류만 바꾸기, 상태만 바꾸기, 둘 다 바꾸기를 각각 확인

```kotlin
// LostFoundAdapter 안 [수업]
private var items: MutableList<LostFoundItem> = mutableListOf()     // 화면에 보일 목록
private var allitems: MutableList<LostFoundItem> = mutableListOf()  // 전체 목록
private var typeFilter = 0
private var statusFilter = 0

fun setFilters(typeFilter: Int, statusFilter: Int) {
    this.typeFilter = typeFilter
    this.statusFilter = statusFilter
    applyFilters()
}

fun applyFilters() {
    val type = when (typeFilter) {
        1 -> LostFoundItem.TYPE_LOST
        2 -> LostFoundItem.TYPE_FOUND
        else -> null                       // 0 = 전체: 조건 없음
    }
    val status = when (statusFilter) {
        1 -> LostFoundItem.STATUS_OPEN
        2 -> LostFoundItem.STATUS_COMPLETED
        else -> null
    }
    val filtered = allitems.filter { item ->
        val matchesType = type == null || item.type == type
        val matchesStatus = status == null || item.status == status
        matchesType && matchesStatus
    }
    submitList(filtered)
}

fun submitList(newItems: List<LostFoundItem>) {
    items = newItems.toMutableList()
    notifyDataSetChanged()                 // 빠뜨리면 화면이 안 바뀜
}
```

- 필터 결과를 `allitems`에 덮어씀 → 한 번 필터하면 전체 목록이 사라짐
- `submitList`에서 `notifyDataSetChanged()` 누락

## 문제 3. 하단 탭에 학교 소식 화면 추가

**중요도 ★★★ / 범위: Navigation (AA_Navigation2 과제 1과 같은 유형)**

### 상황

BottomNavigationView에 홈, 시설, 이용안내 탭이 있는 앱(`BottomNavActivity`)에 "학교 소식" 탭을 하나 더 추가해야 한다.

### 요구사항

1. 새 Fragment `SchoolFragment` 생성 (Blank Fragment)
2. 하단 탭에 "학교 소식" 메뉴가 생기고, 누르면 `SchoolFragment`로 전환
3. 학교 소식 화면은 **최상위(top-level) 화면**이어서 툴바에 뒤로가기 화살표가 **나오지 않아야** 한다.
4. 툴바 제목은 "학교 소식"

### 설계 판단

Navigation 화면 추가는 **파일 4곳을 같은 id로 맞추는 작업**이다. 어느 하나라도 빠지거나 id가 다르면 탭을 눌러도 이동하지 않는다.

| 파일 | 할 일 | 맞춰야 하는 것 |
|---|---|---|
| `SchoolFragment.kt` + `fragment_school.xml` | 화면 자체 | 클래스 이름 |
| `res/menu/bottom_nav_menu.xml` | 탭 메뉴 항목 추가 | `android:id="@+id/schoolFragment"` |
| `res/navigation/mobile_navigation.xml` | 그래프에 목적지 추가 | `android:id="@+id/schoolFragment"`, `android:name`=전체 클래스 경로, `android:label` |
| `BottomNavActivity.kt` | 최상위 화면 집합에 추가 | `AppBarConfiguration(setOf(..., R.id.schoolFragment))` |

- **메뉴 item id와 graph의 fragment id가 같아야** `setupWithNavController()`가 자동으로 연결해 준다. 클릭 리스너를 직접 만들 필요가 없다.
- 툴바 제목은 graph의 `android:label`이 자동으로 쓰인다.
- `AppBarConfiguration`에 넣은 id들은 "최상위"로 취급되어 뒤로가기(Up) 화살표가 표시되지 않는다. 넣지 않으면 학교 소식 화면에 화살표가 생긴다.

### 구현 순서

1. File > New > Fragment > Fragment (Blank) 로 `SchoolFragment` 생성
2. `bottom_nav_menu.xml`에 item 추가
3. `mobile_navigation.xml`에 fragment 추가 (Design 탭에서 추가해도 됨)
4. `BottomNavActivity`의 `AppBarConfiguration`에 `R.id.schoolFragment` 추가
5. 실행: 탭 전환, 툴바 제목, 화살표 없음 확인

## 문제 4. 시설 목록에서 상세 화면으로 데이터 전달

**중요도 ★★★ / 범위: Navigation (AA_Navigation2 시설 화면 확장)**

### 상황

시설 화면(`FacilityFragment`)에 도서관, 학생식당 카드가 있고 오른쪽 화살표(`ivDetail1`, `ivDetail2`)가 있다. 수업 코드에서는 도서관만 상세로 이동한다. 두 시설 모두 같은 상세 화면(`FacilityDetailFragment`)으로 이동하되, **어떤 시설을 눌렀는지에 따라 다른 내용**이 나와야 한다.

### 요구사항

1. `ivDetail1` 클릭 → 상세 화면에 도서관 정보 (이름, 위치 "2호관 3층", 운영시간 "평일 09:00 ~ 21:00")
2. `ivDetail2` 클릭 → 상세 화면에 학생식당 정보 (이름, 위치 "1호관 지하 1층", 운영시간 "평일 11:00 ~ 14:00")
3. 상세 화면은 툴바 뒤로가기 화살표로 시설 목록에 돌아갈 수 있어야 한다.
4. 전달받은 값이 없을 때 앱이 죽으면 안 된다.

### 설계 판단

- 상세 화면을 시설마다 따로 만들지 않는다. **화면은 하나, 데이터(시설 id)만 다르게 전달**한다.
- graph에 `facilityFragment → facilityDetailFragment` **action**을 만들고 `navigate(action id, bundle)`로 이동한다. [수업]
- 전달은 `bundleOf("facilityId" to "library")` 처럼 **키-값**으로 하고, 받는 쪽은 `arguments?.getString("facilityId")`로 같은 키로 꺼낸다. 키 문자열이 한 글자라도 다르면 null이 된다.
- 받는 쪽에서 `when(facilityId)`로 분기해 내용을 채운다.
- 상세 화면은 `AppBarConfiguration`의 최상위 집합에 넣지 **않는다**. 그래야 화살표가 생기고, `onSupportNavigateUp()`이 이전 화면으로 돌려보낸다.
- 수업 코드는 `facilityId!!`를 써서 값이 없으면 앱이 죽는다. 요구사항 4 때문에 `?:`로 기본값을 준다.

### 구현 순서

1. `mobile_navigation.xml`에 action 확인 (Design 탭에서 화살표를 끌어서 만들면 id가 자동 생성됨)
2. `FacilityFragment.onViewCreated`에서 두 화살표에 클릭 리스너 + bundle 전달
3. `FacilityDetailFragment`에서 `arguments`로 꺼내 `when` 분기
4. 실행: 두 시설 각각 이동, 뒤로가기 확인

## 문제 5. 드로어 메뉴와 툴바 뒤로가기

**중요도 ★★ / 범위: Navigation (AA_Navigation2 MainActivity)**

### 상황

같은 3개 화면을 **왼쪽에서 밀어 여는 드로어 메뉴**로도 이동할 수 있게 하고, 툴바 오른쪽 옵션 메뉴에 "설정"을 둔다.

### 요구사항

1. 햄버거 아이콘(≡)을 누르면 드로어가 열리고, 홈/시설/이용안내 메뉴로 이동
2. 현재 화면의 메뉴 항목이 하나만 선택 표시
3. 시설 상세 화면에서는 햄버거 대신 뒤로가기 화살표
4. 툴바 오른쪽 옵션 메뉴 "설정"을 누르면 Toast "설정 화면 준비 중"

### 설계 판단

- 드로어 구성은 xml 3단 구조: `DrawerLayout`(바깥) 안에 **본문(include app_bar_main)** 과 **NavigationView**(`layout_gravity="start"`, `app:menu`, `app:headerLayout`). [수업]
- `AppBarConfiguration(setOf(...), drawerLayout)` 처럼 **두 번째 인자로 drawerLayout**을 주면 최상위 화면에서 햄버거 아이콘이 생긴다. 바텀 내비게이션 버전에는 이 인자가 없다는 점이 차이.
- 하나만 선택 표시는 메뉴 xml의 `<group android:checkableBehavior="single">`.
- "설정"은 화면 이동이 아니라 단순 동작이라 graph와 무관하다. **옵션 메뉴 콜백**(`onCreateOptionsMenu`, `onOptionsItemSelected`)으로 처리한다.

| 비교 | BottomNavigationView | Drawer(NavigationView) |
|---|---|---|
| 레이아웃 | ConstraintLayout 안 아래쪽 | DrawerLayout 안, `layout_gravity="start"` |
| AppBarConfiguration | `AppBarConfiguration(setOf(...))` | `AppBarConfiguration(setOf(...), drawerLayout)` |
| 연결 | `navView.setupWithNavController(navController)` | 같음 |
| 최상위 화면 툴바 | 아이콘 없음 | 햄버거 아이콘 |

### 구현 순서

1. `activity_main.xml` 구조 확인 (DrawerLayout, NavigationView id)
2. `activity_main_drawer.xml` 메뉴 id를 graph id와 맞추고 group 지정
3. `MainActivity`에서 toolbar 설정 → navController → AppBarConfiguration(drawerLayout 포함) → 두 setup 호출
4. `onSupportNavigateUp()` 재정의

## 문제 6. 공지사항 목록 RecyclerView

**중요도 ★★★ / 범위: 어댑터뷰 (RecyclerView 기본 5단계)**

### 상황

학교 소식 화면(또는 메인 화면)에 공지사항 목록을 보여준다. 공지는 제목, 날짜, 중요 여부를 갖고, 중요 공지에만 "중요" 배지가 보인다.

### 요구사항

1. 데이터 클래스 `Notice(title, date, important)`
2. 항목 레이아웃 `item_notice.xml`: 제목 `tvNoticeTitle`, 날짜 `tvNoticeDate`, 배지 `tvBadge`
3. 중요 공지만 배지 표시, 나머지는 배지 숨김(자리도 차지하지 않게)
4. 세로 목록으로 표시. (확장) 2열 그리드로 바꿔 보기

### 설계 판단

RecyclerView는 **필수 3요소(ViewHolder, Adapter, LayoutManager)** 를 갖춰야 화면에 뭐라도 나온다. 순서는 강의자료의 5단계 그대로.

| 단계 | 파일 | 역할 |
|---|---|---|
| 1 | 화면 xml | `<androidx.recyclerview.widget.RecyclerView android:id="@+id/recyclerView">` |
| 2 | `item_notice.xml` | 항목 하나의 모양 |
| 3 | `NoticeViewHolder` | 항목 뷰들을 들고 있다가 `bind()`로 데이터를 채움 |
| 4 | `NoticeAdapter` | 개수(`getItemCount`), 뷰홀더 생성(`onCreateViewHolder`), 데이터 연결(`onBindViewHolder`) |
| 5 | Activity/Fragment | `layoutManager`와 `adapter` 대입 |

- 배지를 "자리도 차지하지 않게" 숨기려면 `View.INVISIBLE`이 아니라 **`View.GONE`**.
- RecyclerView는 뷰홀더를 **재사용**한다. 그래서 `bind()`에서 if만 쓰고 else를 안 쓰면, 재사용된 항목에 이전 배지가 남는다. 표시/숨김 **둘 다** 지정해야 한다.

### 구현 순서

1. `Notice` 데이터 클래스
2. `item_notice.xml` (루트 `layout_height="wrap_content"`)
3. ViewHolder → Adapter
4. 화면에서 샘플 리스트 만들고 연결
5. 실행 후 `LinearLayoutManager`를 `GridLayoutManager(this, 2)`로 바꿔 보기

- `getItemCount()`에서 0 반환(템플릿 그대로)

## 문제 7. 항목 클릭은 상세, 롱클릭은 삭제

**중요도 ★★★ / 범위: 어댑터뷰 + 이벤트 처리 (AA_SQLite의 onItemClick, onItemLongClick 구조)**

### 상황

문제 6의 공지 목록에서, 항목을 누르면 내용을 다이얼로그로 보여주고, 길게 누르면 "삭제할까요?"를 물은 뒤 삭제한다.

### 요구사항

1. 항목 클릭 → AlertDialog로 제목과 날짜 표시
2. 항목 롱클릭 → 확인 다이얼로그. "삭제"를 누르면 목록에서 제거, "취소"면 아무 일 없음
3. 삭제 후 목록이 즉시 갱신
4. 클릭했을 때 **무엇을 할지는 Activity가 결정**하고, 어댑터는 몰라야 한다

### 설계 판단

- 요구 4가 핵심 설계 포인트. 어댑터 안에서 직접 다이얼로그를 띄우면 어댑터가 화면(Activity)에 묶인다. 수업 코드처럼 **함수형 매개변수 `(Notice) -> Unit`** 을 어댑터 생성자로 받아서, 뷰홀더가 클릭될 때 그 함수를 **호출만** 한다. 실제 동작은 Activity가 람다로 넘겨준다. [수업]
- 삭제하려면 목록이 바뀌어야 하므로 어댑터의 리스트를 `List`가 아닌 **`MutableList`** 로 바꾼다.
- 삭제 후 화면 갱신: 수업은 `notifyDataSetChanged()`(전체 다시 그림). [일반] 한 항목만 빠질 때는 `notifyItemRemoved(position)`이 더 효율적이고 사라지는 애니메이션도 나온다. 시험에서는 둘 다 정답이 될 수 있지만 수업 방식인 `notifyDataSetChanged()`를 기본으로 기억.

### 구현 순서

1. 어댑터 생성자에 `onItemClick`, `onItemLongClick` 추가, 리스트를 MutableList로
2. 뷰홀더 생성자에도 두 함수를 넘기고, `bind()`에서 `root`에 클릭/롱클릭 등록
3. 어댑터에 `removeItem()` 추가
4. Activity에서 어댑터를 만들 때 두 람다 전달 (상세 다이얼로그, 삭제 확인 다이얼로그)

<details><summary>모범 구현 보기</summary>

```kotlin
class NoticeViewHolder(
    private val binding: ItemNoticeBinding,
    private val onItemClick: (Notice) -> Unit,
    private val onItemLongClick: (Notice) -> Unit
) : RecyclerView.ViewHolder(binding.root) {

    fun bind(notice: Notice) {
        with(binding) {
            tvNoticeTitle.text = notice.title
            tvNoticeDate.text = notice.date
            tvBadge.visibility = if (notice.important) View.VISIBLE else View.GONE

            root.setOnClickListener { onItemClick(notice) }          // 무엇을 할지는 모름
            root.setOnLongClickListener {
                onItemLongClick(notice)
                return@setOnLongClickListener true
            }
        }
    }
}

class NoticeAdapter(
    private val items: MutableList<Notice>,
    private val onItemClick: (Notice) -> Unit,
    private val onItemLongClick: (Notice) -> Unit
) : RecyclerView.Adapter<NoticeViewHolder>() {

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): NoticeViewHolder {
        val binding = ItemNoticeBinding.inflate(LayoutInflater.from(parent.context), parent, false)
        return NoticeViewHolder(binding, onItemClick, onItemLongClick)
    }

    override fun onBindViewHolder(holder: NoticeViewHolder, position: Int) {
        holder.bind(items[position])
    }

    override fun getItemCount(): Int = items.size

    fun removeItem(notice: Notice) {
        items.remove(notice)
        notifyDataSetChanged()
        // [일반] 대안: val pos = items.indexOf(notice); items.removeAt(pos); notifyItemRemoved(pos)
    }
}
```

## 문제 8. Room으로 메모 저장

**중요도 ★★★ / 범위: SQLite (Room, AA_SQLite와 같은 구조)**

### 상황

간단한 메모 앱. 제목과 내용을 입력해 저장하면 목록에 보이고, **앱을 완전히 껐다 켜도** 목록이 남아 있어야 한다. 최신 메모가 맨 위.

### 요구사항

1. 테이블 `MEMO_T`: id(기본키), title, content, createdAt
2. 앱 시작 시 DB의 메모를 최신순으로 읽어 RecyclerView에 표시
3. 저장 버튼: 제목이 비면 Toast, 아니면 DB에 추가 후 목록 갱신, 입력칸 비우기
4. 메모 롱클릭 시 DB와 목록에서 삭제
5. DB 작업 때문에 화면이 멈추거나 앱이 죽으면 안 된다

### 설계 판단

- "껐다 켜도 남아야" → 메모리 리스트가 아니라 **DB**. 수업 실습 앱이 Room을 쓰므로 Room으로 설계한다.
- Room 3요소를 한 파일(`RoomDB.kt`)에 둔다. [수업]

| 구성요소 | 어노테이션 | 이 문제에서 |
|---|---|---|
| Entity (테이블, 레코드) | `@Entity(tableName = "MEMO_T")`, `@PrimaryKey` | `data class Memo` |
| Dao (DB 작업 메소드) | `@Dao`, `@Query`, `@Insert`, `@Update`, `@Delete` | `interface MemoDao` |
| Database | `@Database(entities = ..., version = 1)` + `RoomDatabase` 상속 | `abstract class MemoDatabase` |

- **요구 5가 핵심**: Room은 메인(UI) 스레드에서 DB 작업을 하면 예외를 낸다. 그래서 DB 작업은 `thread { }` 안에서 하고, 화면 변경(어댑터 갱신, Toast)은 다시 메인 스레드로 넘겨 `Handler(Looper.getMainLooper()).post { }` 안에서 한다. [수업]
- 최신순은 Dao의 SQL에서 `ORDER BY createdAt DESC`로 해결한다. 코드에서 정렬할 필요 없음.
- 기본키: 수업은 `@PrimaryKey var id: Long`에 `System.currentTimeMillis()` 기반 값을 직접 넣었다. [일반] `@PrimaryKey(autoGenerate = true)`로 두면 0을 넣어도 자동 증가한다. 둘 중 하나로 일관되게.
- 라이브러리: 수업 완성 프로젝트(AA_SQLite)의 `build.gradle.kts`는 `room-runtime`, `room-ktx`를 `implementation`, `room-compiler`를 **`ksp`** 로 추가했다. (슬라이드는 annotationProcessor/kapt로 설명)

### 구현 순서

1. `build.gradle.kts`에 Room 의존성 확인 후 Sync
2. `RoomDB.kt`: Entity → Dao → Database
3. 어댑터에 `allitems`를 두고 `loadItems(dao)`, `addItem(item, dao)`, `deleteItem(item, dao)` 작성 (각각 thread + Handler)
4. Activity에서 database, dao 생성 → 어댑터 연결 → `loadItems` 호출
5. 저장 버튼, 롱클릭 연결
6. 실행: 메모 2개 저장 → 앱 완전 종료 → 다시 실행해서 남아 있는지 확인

```kotlin
        val list = dao.getAll()

    }
```

### 동작 흐름

앱 시작 → `Room.databaseBuilder(...).build()`로 DB 객체 생성(파일이 없으면 만들고 있으면 연다) → `memoDao()`로 Dao 획득 → `loadItems`가 작업 스레드에서 `SELECT ... ORDER BY createdAt DESC` 실행 → 결과를 Handler로 메인 스레드에 넘겨 목록 표시. 저장 시에도 같은 패턴: **DB는 thread 안, 화면은 Handler.post 안**. Room은 Dao 인터페이스의 어노테이션을 보고 실제 SQL 코드를 컴파일할 때 자동 생성한다(그래서 compiler 라이브러리가 필요).

### 시험 빈칸 후보

- `@Entity(tableName = "MEMO_T")`, `@PrimaryKey`
- `@Query("SELECT * FROM MEMO_T WHERE id = :memoId")` 의 `:변수명` 바인딩
- `@Database(entities = arrayOf(Memo::class), version = 1)`, `abstract fun memoDao(): MemoDao`
- `Room.databaseBuilder(applicationContext, MemoDatabase::class.java, "memo_db").build()`
- `thread { }`, `Handler(Looper.getMainLooper()).post { }`

### 자주 하는 실수

- `dao.getAll()`을 `thread` 밖에서 호출 → "메인 스레드에서 DB 접근 불가" 예외로 앱 종료
- `thread` 안에서 `notifyDataSetChanged()`나 Toast 호출 → 메인 스레드가 아니라서 오류
- `@Database`의 클래스를 `abstract`로 안 만듦, Dao를 `interface`로 안 만듦
- 기본키 값이 같은 메모를 두 번 insert → 기본키 충돌 예외

## 문제 9. SQLiteOpenHelper와 Contract 클래스로 연락처 저장

**중요도 ★★ / 범위: SQLite (강의자료 7의 활용법 1, 2)**

### 상황

Room 없이 SQLite를 직접 써서 연락처(이름, 전화번호)를 저장하고 목록으로 보여준다. 테이블 이름, 컬럼 이름, SQL을 여러 곳에 흩어 쓰지 않도록 관리해야 한다.

### 요구사항

1. 테이블 `CONTACT_T`: ID(INTEGER 기본키), NAME(TEXT NOT NULL), PHONE(TEXT)
2. 테이블 이름, 컬럼, SQL 문장은 **Contract 객체 한 곳**에 상수로 둔다
3. 추가 버튼: 입력값을 DB에 insert 후 목록 다시 읽기
4. 목록은 Cursor로 읽어 RecyclerView에 표시
5. 항목 롱클릭: 해당 ID 레코드 delete
6. Activity가 끝날 때 helper를 닫는다

### 설계 판단

- Contract 클래스: 이름이 바뀌어도 **상수 한 곳만** 고치면 되게 하는 설계. [수업 슬라이드]
- SQLiteOpenHelper를 상속하면 DB 파일 경로를 직접 다루지 않아도 되고 **버전 관리**(`onUpgrade`)를 할 수 있다.
- 쓰기 작업(insert/update/delete)은 `writableDatabase`, 읽기는 `readableDatabase`.
- 값 넣기는 SQL 문자열을 이어 붙이지 말고 **`ContentValues`** 에 `put(컬럼, 값)`. 조건 삭제는 `where = "ID = ?"`, `whereArgs = arrayOf(id.toString())` 로 `?` 자리에 값을 넣는다.
- Cursor는 `while (cursor.moveToNext())`로 한 행씩 이동하며 `getInt`, `getString`으로 읽는다. 다 쓰면 `close()`.

| 메소드 | 시그니처 (파라미터 순서가 수기 출제 1순위) |
|---|---|
| insert | `insert(String table, String nullColumnHack, ContentValues values)` |
| update | `update(String table, ContentValues values, String where, String[] whereArgs)` |
| delete | `delete(String table, String where, String[] whereArgs)` |
| rawQuery | `rawQuery(String query, String[] queryArgs)` |

### 구현 순서

1. `ContactContract` 객체 (상수)
2. `DBHelper : SQLiteOpenHelper` (`onCreate`, `onUpgrade`)
3. 데이터 클래스 `Contact(id, name, phone)` + 어댑터 (문제 7 구조)
4. Activity: helper 생성 → `loadContacts()` → 추가, 삭제 → `onDestroy`에서 close

```kotlin
object ContactContract {
    const val TABLE_NAME = "CONTACT_T"
    const val COL_ID = "ID"
    const val COL_NAME = "NAME"
    const val COL_PHONE = "PHONE"

    const val SQL_CREATE_TABLE = "CREATE TABLE IF NOT EXISTS $TABLE_NAME (" +
            "$COL_ID INTEGER NOT NULL PRIMARY KEY, " +
            "$COL_NAME TEXT NOT NULL, " +
            "$COL_PHONE TEXT)"
    const val SQL_DROP_TABLE = "DROP TABLE IF EXISTS $TABLE_NAME"
    const val SQL_LOAD = "SELECT * FROM $TABLE_NAME"
}

class DBHelper(context: Context?) : SQLiteOpenHelper(context, DB_FILE, null, DB_VERSION) {
    override fun onCreate(db: SQLiteDatabase) {                      // DB 처음 만들 때
        db.execSQL(ContactContract.SQL_CREATE_TABLE)
    }

    override fun onUpgrade(db: SQLiteDatabase, oldVersion: Int, newVersion: Int) {   // 버전이 오를 때
        db.execSQL(ContactContract.SQL_DROP_TABLE)
        onCreate(db)
    }

    companion object {
        const val DB_FILE = "contact.db"
        const val DB_VERSION = 1
    }
}

data class Contact(val id: Int, val name: String, val phone: String)
```

```kotlin
// MainActivity
private lateinit var dbHelper: DBHelper
private val contacts = mutableListOf<Contact>()
private lateinit var adapter: ContactAdapter

override fun onCreate(savedInstanceState: Bundle?) {
    // ... binding 준비
    dbHelper = DBHelper(baseContext)
    adapter = ContactAdapter(contacts) { contact -> deleteContact(contact) }   // 롱클릭 람다
    binding.recyclerView.layoutManager = LinearLayoutManager(this)
    binding.recyclerView.adapter = adapter
    loadContacts()

    binding.btnAdd.setOnClickListener {
        val db = dbHelper.writableDatabase
        val values = ContentValues()
        values.put(ContactContract.COL_ID, (System.currentTimeMillis() % 1000000).toInt())
        values.put(ContactContract.COL_NAME, binding.etName.text.toString())
        values.put(ContactContract.COL_PHONE, binding.etPhone.text.toString())
        db.insert(ContactContract.TABLE_NAME, null, values)
        loadContacts()
    }
}

private fun loadContacts() {
    contacts.clear()
    val db = dbHelper.readableDatabase
    val cursor = db.rawQuery(ContactContract.SQL_LOAD, null)
    while (cursor.moveToNext()) {
        val id = cursor.getInt(0)            // 컬럼 순서: ID, NAME, PHONE
        val name = cursor.getString(1)
        val phone = cursor.getString(2)
        contacts.add(Contact(id, name, phone))
    }
    cursor.close()
    adapter.notifyDataSetChanged()
}

private fun deleteContact(contact: Contact) {
    val db = dbHelper.writableDatabase
    db.delete(ContactContract.TABLE_NAME, "${ContactContract.COL_ID} = ?", arrayOf(contact.id.toString()))
    loadContacts()
}

override fun onDestroy() {
    dbHelper.close()
    super.onDestroy()
}
```

### 동작 흐름

`DBHelper(baseContext)` 생성 → 처음 `writableDatabase`/`readableDatabase`를 요청하는 순간 파일이 없으면 `onCreate`가 호출되어 테이블 생성 → insert는 `ContentValues`의 컬럼-값 쌍으로 한 행 추가 → `rawQuery`가 Cursor(결과 표의 커서)를 돌려주고 `moveToNext()`가 false가 될 때까지 한 행씩 읽음 → DB_VERSION을 2로 올리면 다음 실행 때 `onUpgrade` 호출.

### 시험 빈칸 후보

- `SQLiteOpenHelper(context, DB_FILE, null, DB_VERSION)` 매개변수 4개
- `db.insert(TABLE_NAME, null, values)` 두 번째 인자 null
- `db.delete(TABLE_NAME, "ID = ?", arrayOf(...))`
- `while (cursor.moveToNext())`, `getInt(0)`, `getString(1)`
- `CREATE TABLE IF NOT EXISTS`, `onUpgrade(db, oldVersion, newVersion)`

### 자주 하는 실수

- 같은 ID로 두 번 insert → 기본키 충돌로 insert가 -1 반환 (예외 없이 조용히 실패)
- `cursor.close()` 누락
- 컬럼 인덱스를 1부터 셈 → `getInt(0)`이 첫 컬럼
- 문제 8과 달리 이 예시는 메인 스레드에서 DB를 쓴다. SQLiteOpenHelper는 메인 스레드 접근을 막지 않지만, 데이터가 많으면 화면이 멈출 수 있다 (Room은 아예 막음)

| 요구 | 구성요소 | 근거가 되는 수업 코드 |
|---|---|---|
| 1, 4 | Room Dao `getAll`(ORDER BY), `delete` + thread/Handler | AA_SQLite `loadItems`, `deleteItem` |
| 2, 3 | 다이얼로그 함수 **하나** `showBookFormDialog(existingItem: BookRecord?)`, null이면 등록 | AA_SQLite `showItemFormDialog`, `saveFromDialog` |

| 5 | 어댑터가 `allitems`/`items` 두 리스트 + `applyFilters()` | AA_SQLite `applyFilters` |
| 5 수정 후 반영 | **`updateItem` 후 `applyFilters()` 호출** | 수업 코드는 `notifyDataSetChanged()`만 해서 필터 중 상태를 바꾸면 안 맞는 항목이 남는다. 이 부분을 개선 |

| 8 | ViewHolder `bind`에서 `currentUser`와 비교 | AA_SQLite `tvOwner` |

**설계 핵심 두 가지**

1. 등록과 수정은 **같은 폼, 같은 함수**. 차이는 3가지뿐이다: 제목 문구, 폼을 기존 값으로 채우느냐, 저장 시 insert냐 update냐. 이 차이를 `existingItem == null` 하나로 분기한다.
2. 어댑터는 **DB 작업과 화면 반영을 함께 책임**진다(수업 구조). Activity는 "추가해라, 삭제해라"만 부르고 thread/Handler는 어댑터 안에 숨긴다.

| 순서 | 할 일 | 확인 방법 |

| 1 | `RoomDB.kt` Entity, Dao, Database | 빌드 성공 (빨간 줄 없음) |

```kotlin
        val binding = ItemBookBinding.inflate(LayoutInflater.from(parent.context), parent, false)
        return BookViewHolder(binding, currentUser, onItemClick, onItemLongClick)
    }

    override fun onBindViewHolder(holder: BookViewHolder, position: Int) {
        holder.bind(items[position])
    }

    override fun getItemCount(): Int = items.size

    fun submitList(newItems: List<BookRecord>) {
        items = newItems.toMutableList()
        notifyDataSetChanged()
    }

    fun loadItems(dao: BookDao) {
        thread {
            val list = dao.getAll()
            Handler(Looper.getMainLooper()).post {
                allitems = list.toMutableList()
                applyFilters()
            }
        }
    }

    fun addItem(item: BookRecord, dao: BookDao) {
        thread {
            dao.insert(item)
            Handler(Looper.getMainLooper()).post {
                allitems.add(0, item)                 // 최신순 유지
                applyFilters()
            }
        }
    }

    fun updateItem(item: BookRecord, dao: BookDao) {
        thread {
            dao.update(item)
            Handler(Looper.getMainLooper()).post {
                applyFilters()                        // 수업 코드 개선: 상태 변경을 필터에 반영
            }
        }
    }

    fun deleteItem(item: BookRecord, dao: BookDao) {
        thread {
            dao.delete(item)
            Handler(Looper.getMainLooper()).post {
                allitems.remove(item)
                applyFilters()
            }
        }
    }

    fun setFilter(statusFilter: Int) {
        this.statusFilter = statusFilter
        applyFilters()
    }

    private fun applyFilters() {
        val status = when (statusFilter) {
            1 -> BookRecord.STATUS_READING
            2 -> BookRecord.STATUS_DONE
            else -> null
        }
        submitList(allitems.filter { status == null || it.status == status })
    }
}
```

### 동작 흐름 (사용자 시나리오로 따라가기)

1. **앱 실행** → DB 생성 → `loadItems`가 작업 스레드에서 전체 조회 → 메인 스레드에서 `allitems`에 저장 후 필터(전체) 적용 → 목록 표시
2. **등록 버튼** → `showBookFormDialog(null)` → 제목 "등록", 빈 폼 → 저장 → `existingItem == null`이므로 새 `BookRecord` 생성 → `addItem` → DB insert 후 `allitems` 맨 앞에 추가 → 필터 적용 → 목록에 나타남
3. **항목 클릭** → 어댑터가 Activity가 준 람다 호출 → `showBookFormDialog(item)` → 작성자 검사 통과 → 폼에 기존 값 → 저장 → 같은 객체의 값을 바꿔 `updateItem` → DB update → `applyFilters()`로 현재 필터 다시 적용
4. **"읽는 중" 필터 상태에서 어떤 책을 완독으로 수정** → `applyFilters()` 덕분에 그 책이 목록에서 빠짐 (수업 코드 그대로면 남아 있음)
5. **롱클릭** → `deleteItem` → DB delete, `allitems`에서 제거 → 필터 적용

### 이 문제에서 나올 만한 수기, 빈칸

- `AlertDialog.Builder(this).setView(dialogBinding.root).create()` 와 `dialog.show()`, `dialog.dismiss()`
- `DialogBookFormBinding.inflate(layoutInflater)` (다이얼로그도 ViewBinding으로 inflate)
- `existingItem: BookRecord?` 의 `?` (null 허용)
- `ratingForm.rating`, `rbDone.isChecked`
- `Room.databaseBuilder(...)`, `@Query`의 `ORDER BY createdAt DESC`
- `allitems.filter { status == null || it.status == status }`

### 확장 과제 (시간 남으면)

- 요약 TextView "전체 n권 / 완독 m권": `applyFilters()` 끝에서 Activity가 넘겨준 콜백 `(Int, Int) -> Unit`을 호출하는 방식으로 설계 (어댑터가 Activity 뷰를 직접 건드리지 않게)
- 롱클릭 즉시 삭제 대신 문제 7의 확인 다이얼로그 적용
- 문제 3처럼 BottomNavigationView를 붙여 "기록" 탭과 "통계" 탭으로 나누기 (이 경우 DB 작업은 각 Fragment에서 `requireContext()`로 database 생성)
